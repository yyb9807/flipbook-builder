# 第九轮计划：真实本地模型基线与生成质量优化

制定于 2026-10-19，实施前基线 `71535c9`，分支 `codex/live-model-quality`。先完成本计划与评估合约，再运行原生产行为的真实基线，依据实际失败优化，不预填模型成绩。

## 模型、范围与运行边界

- 当前没有项目 `.env`、可用模型凭据或已运行的本地模型服务。本轮采用本机 Apple Silicon / 24 GB 内存，在独立临时环境运行 `mlx-community/Qwen3-VL-2B-Instruct-4bit`。按[模型发布页](https://huggingface.co/mlx-community/Qwen3-VL-2B-Instruct-4bit)与[MLX-VLM 项目](https://github.com/Blaizzy/mlx-vlm)核对许可、精确权重 revision、依赖版本与实际 HTTP 协议。权重约 1.8 GB，不进入仓库；服务只监听 localhost，不使用其他产品登录凭据。
- 这是该本地量化模型在固定小样例上的真实推理，不代表所有供应商或模型。API 费用为 0；记录推理次数、预留输出 token、实际服务用量和时间，不能把预留量写成实际用量。
- 冻结现有 `quality-v1` 的六份中英文素材、事实、禁止结论、真值框和回放字节，数据集摘要不变。基线与候选各最多 18 次生成、66,400 个预留输出 token，累计执行上限 1,800 秒，单请求仍最多 120 秒。本地服务跨重启最多接收 42 次推理：基线/候选各 18、能力探测最多 2、真实产品验收最多 4；受控假供应商回归另计。能力探测单独计数，不隐藏重试、补答或结构修复调用。失败、缺页和未知结果如实保留。

## 先冻结评估方法

1. 保留现有精确标签选择默认行为；增加显式 `first-hotspot` 策略，确定地沿当前输出的首个入口探索三层，不将案例答案或预期标签注入生产提示词。两次运行用同一策略，记录实际标签、上下文、来源和请求摘要。该策略固定探索程序，不保证两次恰好展开同一主题；不同实际主题仍标为不可直接比较，不放松原比较门槛或宣称全套提升。
2. 增加明确的 `agent` 评审身份、执行者/模型信息和独立 `agent_quality`，始终保持未发生的人工评审为 `not_reviewed`。逐项事实和禁止结论与四维分数分别记录；引用实际页 ID、区块 ID 与原文摘录，根页必需事实不能用子页补足。评审证据先验证定位与文字，再由独立 Agent 依据固定素材判断语义，不把关键词命中当事实通过。
3. 在真实基线前冻结评估器、报告和策略；之后优先仅改生产生成代码。若发现必须修改方法的缺陷，保留原始运行并同时重新评估两侧，明确版本变化，不能混用评审。方法参考[官方评估指南](https://developers.openai.com/api/docs/guides/evaluation-best-practices)，实现不依赖外部评估平台。

## 基线与有依据的优化

- 先以现有生产 Agent 行为完成真实 baseline，保存未经改写的响应与规范化结果；逐页检查正文是否解释机制、热点是否准确/可深入，以及三层是否重复、矛盾或丢失条件。图片保留实际预测框，不按真值修正。
- 只有实际发现的问题才进入实现。可能的方向包括更明确的解释任务、区块入口区分、来源/未知边界的跨页保留及图片完整边界描述，不把固定案例的人名、数字、标签或真值坐标写进通用提示词。
- 如需扩展跨页上下文，使用有界公共构造器，区分原始用户素材、当前父页概览、所选区块与已覆盖主题；生产任务在入队时冻结，评估器调用同一构造器，不从执行时最新页面补料。
- 新行为显式记录生成修订；没有新标记的已有任务继续原路径，已完成 checkpoint 不重新调用。保留 DBOS 工作流名称、步骤顺序、现有正文合约和未知调用保护，不通过修改解析器掩盖模型内容失败。
- 候选使用相同权重、运行参数、素材与额度。报告真实变化、退化和仍未通过的项；路径不一致时按可比案例或单侧诊断呈现，不伪造整体胜出。

## 验收与交付

1. 离线评估全套、Agent 身份/摘录定位/分支策略负例、实际 HTTP 提示词/上下文一致性与一次分发保护。
2. 新旧冻结任务兼容、上下文有界和来源条件保留的针对性测试；全量后端隔离 Postgres、Ruff。若改产品上下文，完整生成恢复、历史与固定发布进程验收；前端 lint、测试、播放器、构建保留完整回归。
3. 实际浏览器桌面/390px 检查真实输出、热点框、评审依据与比较；使用仅含测试素材的项目验证三层阅读、编辑/恢复、导出与固定发布。产品功能的受控供应商验收与真实模型内容基线分别记录。
4. 完成独立审查，更新当前文档、模型/运行版本、证据、失败清单与实施报告。默认运行数据不入库，只保存经检查的非敏感基线摘要和明确许可的测试示例。保持 GitHub Actions 已移除。

## 基线后的实施决定

2026-10-19 实际完成原生产行为 18/18 次生成，运行摘要 `6f7ba4775263e2768afca9ead8cab4fd87f75b951c492c2056629d78aa6eb0eb`；此前仅有两次能力探测。以下决定来自实际输出，不是预设评分：

- 三个英文案例的 9 页均为中文：将 `en` / `zh` 明确展开为自然语言名称，约束所有读者可见字段。
- 预约中文子页出现“具体领取时间及地点将另行通知”，孙页出现“先到先得”；英文案例子页出现候补，均没有原素材依据。新任务冻结有界原始用户素材、祖先标题、父页概览、所选正文及已覆盖标题，明确模型生成内容不能升级为原始事实。
- 两个图片根页给出相同粗框，例如圆形 `(0.1, 0.2, 0.2, 0.15)`，三角形 `(0.5, 0.2, 0.2, 0.15)`，未覆盖实际对象。新版图片提示移除容易照抄的示例坐标，要求按真实完整轮廓分别估计四条边；不改变解析器、不校正到标注真值。
- 正文存在重复和无依据的概括，例如孙页把沸腾说成“所有分子均达到逃逸能级”。新版强调保留成立条件、每区块只解释一个具体问题，逐层添加机制/区别/限制，不靠补造细节满足篇幅。

上述新行为以内部 `grounded-v2` 生成修订标记仅用于新入队任务。缺少标记的已保存任务使用原提示词和上下文；现有工作流和正文格式合约保持兼容。独立逐项评审正在并行核对，候选运行前完成生产补丁审查与针对性回归。

运行偏差记录：首次候选目录 `round9-live-candidate` 在首个请求连接本地服务时失败（ConnectError）。评估器保守记录为 `outcome_unknown`，预留 4,000 输出 token，原检查点不修改也不恢复。核对服务日志仅有此前 20 条完整 admission/finished、无第 21 次接收，且本机端口拒绝连接，确认这次没有模型推理。由主代理重启相同服务、相同持久额度文件，显式新建 `round9-live-candidate-2` 完整候选；两者分别披露，不能隐去前次意图。正式候选仍最多 18 次接收与 66,400 预留输出 token；候选阶段的客户端意图合计最多 19 次、70,400 预留 token，其中启动失败的 4,000 不是实际用量。全轮服务接收上限仍为 42，无静默重试或额度重置。首次服务退出原因未查明，不能断言为模型超时。

## 评估后的发布决定

两侧逐项 Agent 评审均为 6/6 未达标，人工未审；实际展开路径不同，不能宣称整体提升。候选只改善一个英文案例的输出语言，仍存在无依据规则、重复和定位失败。因此调整原定新任务启用方案：生产默认保持原 v1，仅服务器显式设置 `KNOWLEDGE_GENERATION_REVISION=grounded-v2` 后，新任务才冻结实验修订；已有任务兼容规则不变。完整默认流程验收和最终证据见[实施报告](ROUND_9_IMPLEMENTATION.md)。
